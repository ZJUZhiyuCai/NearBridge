## 日常使用

首次扫码配对后，在 Mac“手机”页开启蓝牙通道，手机右上角“··· → 连接与设置 → 仅蓝牙”选择 Mac；选过的设备会保留。自动模式优先尝试局域网，失败时尝试已选蓝牙 Mac；仅蓝牙模式不使用局域网。重连先尝试记住的设备，失败才扫描。连续三轮失败后暂停，可点“重新连接蓝牙”。首次 NearBridge 身份配对仍使用局域网扫码流程。

手机目前需要保持前台。正在上传、下载或连接自检时，只对 NearBridge 前台窗口保持亮屏；结束或退到后台后释放，不修改系统锁屏设置。“检查蓝牙连接”会在 Mac 留下一份 32 KB 测试文件，校验回传后清理手机临时副本。蓝牙适合文字、工作流和小文件；照片合集、视频等建议使用局域网。

- `蓝牙直传验证.bin`（1,048,909 字节）此前的收件回执来自局域网 TCP 连接。它**不是**蓝牙传输证据。

## BLE 通道实现

- 服务 UUID `b4525100-17b0-4cb4-96a6-06c73a620c31`，写入特征 `...5101...`，指示特征 `...5102...`。
- 单条 BLE 链路承载最多 4 条 TLS 字节流。每帧为类型、非零流 ID 和负载：`1` 打开，`2` 确认打开，`3` 数据，`4` 关闭。
- 手机到 Mac 使用有回应写入；Mac 到手机使用 GATT indication，并处理 CoreBluetooth 发送队列背压。按协商 MTU 分帧，单帧最大 512 字节，队列和每流缓冲均有界，闲置流在 120 秒后关闭。
- 手机只监听 `127.0.0.1:53320`，Mac 只转发到原生手机 TLS 端口 `127.0.0.1:53320`。管理端口 53318 不可通过蓝牙访问。
- 现有私有 CA、公钥 pin、配对会话和 SHA-256 均保留。BLE 发现结果不可信，凭证只有在 TLS 身份验证后才能发送。仅蓝牙模式不会改走局域网；自动模式会明确显示当前线路。
- 蓝牙传输请求使用 64 KiB 文件分块。断链/初始化失败采用有限退避，连续三轮失败后停止自动尝试，由“连接与设置 → 重新连接蓝牙”恢复。Mac 检测到系统蓝牙重置时关闭实验通道并取消下次启动自动开启。
- 连接切换/应用暂停时使在途请求失效，避免迟到的局域网响应把界面误标成“纯蓝牙直传”。

## 检查结果与待验收项

早期 `npm test` 22 项通过，包括实际 Swift 编码器的协议向量、畸形帧拒绝、多种 MTU 的无损重组；字节中继测试验证正确 CA、错误 CA 拒绝、配对身份和管理接口隔离。它们不替代蓝牙硬件测试。

两端构建、手机调试签名和覆盖安装通过。手机增加 `ACCESS_BLUETOOTH` 权限，Mac 使用系统蓝牙权限。

后续仍需验证：

1. 多个 64 KiB 分块的大文件、不同类型文件、实际持续速率和长时间稳定性。
2. 主动断开蓝牙、切换后台、系统锁屏、杀进程及多设备场景的完整恢复矩阵；当前只验证了正常回前台和覆盖更新后重连。
3. 背压极限、手机存储不足与错误证书的手机侧负向验证；现有服务端和帧协议自动化测试不能替代这些硬件场景。
